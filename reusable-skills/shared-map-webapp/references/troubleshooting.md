# 장애 진단 사례

## 1. 지도는 연결했는데 공유 링크 불러오기는 실패

지도 SDK와 장소 메타데이터 조회는 별도 경로다. 서버의 공유 링크 해석 → place ID 추출 → upstream 응답 → 필드 정규화 단계를 나눠 확인한다.

이 사례에서는 `data.data.placeDetail` 중첩 응답을 읽고 ID/name/coordinate를 검증해야 했다. 지도 웹사이트의 `/p/api/place/summary/{id}`를 사용했으나 이는 **공식 Open API 계약이 아닌 공개 웹 조회 경로**다. 향후 구조 변경/차단이 가능하므로 adapter를 서버 한 곳에 격리한다. 안정적인 제공 API가 있다면 그것을 우선한다.

- 단축 링크 리다이렉트마다 목적지 호스트를 재검증한다. HTTPS, 허용 네이버 호스트, credentials/임의 port 금지, 최대 hop/시간/입력 길이를 제한한다.
- 일반 HTTP 실패/429/timeout/HTML 응답/ID 불일치/좌표 누락을 구분한다. 실패를 성공이나 '장소 없음'으로 둔갑시키지 않는다.
- 연락처가 없으면 빈 값이다. 지도 인증 실패와 장소 수집 실패를 하나의 원인으로 단정하지 않는다.

## 2. 첫 클릭만 이동하지 않음

SDK script onload와 실제 Map 생성 완료는 다르다. 이 사례에서는 SDK callback 직후 생성자가 아직 준비되지 않아 `queueMicrotask` 후 초기화하고 Map의 `init` 이벤트까지 기다렸다. 선택 의도(group/place/user)를 준비 전에 저장하고 준비 후 적용한다. 초기화 Promise를 재사용해 지도 객체를 중복 생성하지 않는다. 실패 시 script/타이머/Promise 상태를 정리해 재시도 가능하게 한다.

## 3. 매번 '다른 기기에서 변경됨'이 뜸

두 기기 충돌인지, 읽기 revision이 write precondition에 적합한지 구분한다. 이 사례에서 압축된 Blob 응답은 `W/`로 시작하는 weak ETag를 반환할 수 있었고 strong If-Match 비교가 계속 실패했다.

검증된 조합: private `get`에 `useCache:false`, `headers: {'accept-encoding':'identity'}`를 전달하고 Blob의 ETag를 그대로 `put`의 `ifMatch`로 전달한다. 최초 생성은 `allowOverwrite:false`. 최초 생성 경쟁도 충돌로 처리한다. **W/ 접두사를 임의 삭제하거나 조건부 쓰기를 제거해 해결하지 않는다.** SDK 버전별 동작을 모의 HTTP 응답 테스트로 재검증한다.

- 성공 전 로컬 원본을 갱신하지 않는다. clone → 변경 → 조건부 PUT → 성공 시 state 교체 순서다.
- 409이면 최신 상태를 다시 읽고 사용자의 입력을 보존한다. 자동 덮어쓰기/무한 재시도는 금지한다.
- 동일한 실패 문구가 실제 동시 수정의 증거는 아니다. gzip 여부·캐시·revision 전달·누락을 확인한다.
- 이 사례의 ETag 원인은 코드와 요청으로 검증했다. 운영 무변경 PUT도 서버 변경이므로 일반 smoke test에서는 수행하지 않는다.

## 4. 다른 기기에서 데이터가 안 보임

localStorage는 브라우저별이다. 공유 저장소와 revision을 갖는 서버 API가 필요하다. 모든 방문자 CRUD 요구에는 공용 저장을 적용했지만, 읽기 전용 기본 UI와 편집 헤더는 실수 방지일 뿐 인증은 아니다. 비공개 서비스 요구가 생기면 서버 인증·권한을 별도로 설계한다.

## 5. 모바일 상세 링크가 안 열림

저장된 URL이 PC용 `/p/entry/place/...`이고 `_blank`로 열리고 있었다. 모바일에서는 place ID로 `https://m.place.naver.com/place/{id}/home`을 구성해 `_self`로 이동시켰다. ID를 모르면 검증된 원래 공유 URL을 유지한다. 모바일 장소 페이지 도착을 실제 브라우저에서 확인했다.

이 사례에서 사용자 기기의 정확한 근본 원인이 새 창 차단인지 PC 주소 호환성인지는 확정하지 못했다. '새 창이 원인으로 입증됨'이라고 재서술하지 않는다. 앱 직접 실행은 설치 여부와 fallback이 필요한 별도 작업이다.

## 6. 배포 후 예전 HTML + 새 JS가 섞임

실제 운영 응답과 로컬 정적 파일을 비교한다. 이 세션의 내장 브라우저에서 과거 탭 캐시가 남은 경우 query가 다른 새 탭으로 검증했다. 쿼리 추가는 진단법이지 캐시 설계의 영구 대책이 아니다. 일반 서비스는 해시 파일명과 HTML 재검증 정책으로 버전 혼합을 방지한다.

네트워크 실패를 해결하려고 무조건 CORS를 해제하거나 클라이언트로 서버 비밀키를 옮기지 않는다.
