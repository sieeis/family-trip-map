# 데이터 처리와 검증

## 일괄 장소 입력

이 사례는 줄당 URL 한 개, 최대 50개, 동시 조회 2개로 제한했다. 입력 단계에서 동일 링크를 제거하고 조회 후 place ID로 short/direct alias 중복을 제거한다. 결과 순서는 응답 도착순이 아닌 입력순이다. 현재 그룹의 기존 장소도 중복에서 제외한다. 다른 그룹에 같은 장소를 넣는 것은 허용했다.

성공/실패/잘못된 링크/중복/대기/진행 상태를 구분한다. 실패만 재시도하고 성공 결과를 재조회하지 않는다. 모달을 닫으면 AbortController로 취소하고 늦은 응답이 닫힌 화면이나 저장 상태를 바꾸지 못하게 한다. 사용자가 결과를 검토한 후 성공 건을 한 번의 조건부 PUT으로 저장한다. 충돌 시 검토 결과를 보존해 재시도할 수 있어야 한다.

## 공유 편집

기본 읽기 전용, 자물쇠로 편집 전환. 저장 pending 동안 중복 클릭과 편집 전환을 막는다. 사용자가 요청하지 않은 인증 모델로 바꾸지 않되 비공개 권한 요구와 단순 잠금을 구분한다. 15초 폴링 같은 수치는 이 사례의 선택이며 새 프로젝트의 요금/규모에 맞게 조정한다. 모달 입력 중 refresh가 draft를 덮어쓰지 않게 한다.

## 내보내기와 순서

- 선택 그룹과 소속 장소만 한 표로 내보낸다. 내부 ID/revision/좌표 등 화면에 없는 metadata는 이 사례에서 제외했다.
- JSON, Markdown, XLSX 및 ZIP을 지원했다. XLSX는 한 시트/한 표, 공유 URL hyperlink, 전화번호 문자열 유지. '=...' 같은 사용자 문자열을 수식으로 변환하지 않는다.
- 빈 그룹도 그룹 정보를 가진 한 행으로 내보낸다. 잘못된 group ID는 404, 누락은 400처럼 처리한다.
- 보고서용 JSON과 복원용 snapshot은 다르다. 보고서를 백업이라고 부르거나 그대로 import 가능하다고 약속하지 않는다.
- D&D는 ID 기반 순서 변경으로 구현하고 필터로 숨겨진 항목의 슬롯/메타정보를 보존한다. 키보드 이동과 터치 핸들을 제공한다. 정렬 모드에서 수동 이동하면 사용자 순서로 전환한다.

## 필수 회귀 시나리오

1. 두 클라이언트가 같은 revision에서 수정 → 한쪽 성공, 다른 쪽 409; 최신 내용 유지.
2. 네트워크 저장 실패 → 서버와 로컬 확정 상태 모두 이전 상태 유지, draft 보존.
3. weak/strong ETag 읽기와 조건부 PUT, 최초 생성 경쟁.
4. SDK 준비 전 첫 장소 선택 → init 후 중심 이동; 같은 snapshot 재렌더링은 카메라 유지.
5. 같은 목록 재클릭 → 전체; 핀 클릭 → 팝업 없음; 상세 버튼 → 해당 장소 팝업.
6. 겹친 카드 숨김, zoom 후 분리 표시, 선택 카드 강제 표시, 화면 끝 clamp.
7. 현재 위치 이동 시 setZoom 호출 수 변화 없음; 위치 watch 갱신은 카메라 유지.
8. bulk concurrency/alias duplicate/partial failure/retry/abort/한 번 저장.
9. 내보내기 단일 그룹·단일 표·전화번호 앞 0·URL·한글·개행·문자열 수식 보존.
10. 모바일 링크의 실제 목적지와 _self, PC 링크 _blank. 인앱 브라우저·OS 앱 실행은 별도 실기기 검증.

운영 데이터에 테스트 장소를 추가하지 않는다. 쓰기 검증은 mock store나 별도 preview 데이터로 수행한다. UI 확인은 읽기 전용 탐색과 개인 화면 상태로 할 수 있다.

## 배포 완료 판단

관련 테스트 성공 → 요청된 대상에 배포 → READY/alias 확인 → 공개 HTML/JS/CSS 확인 → 실제 UI 동작 확인 순서다. 배포가 성공해도 JS 초기화 오류나 캐시 혼합은 남을 수 있다. 최종 답변에는 변경 내용, 실제 검증 범위, 실기기에서 확인하지 못한 부분만 간결히 적는다.

이 패키지의 스크립트는 배포하지 않는다. 점검 결과 OK가 실제 지도 인증/Blob 쓰기/사용자 위치/네이버 앱 실행 성공을 보장하지 않는다.
